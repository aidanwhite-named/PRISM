# GPT 설계·구현 요청 — 2차 조각: Claim Element / Element Mapping 영속화

(1차 조각 = 정답 라이브러리, 완료. 이 문서는 그 다음 조각이다.)

---

## 0. 역할과 이번 요청의 범위

너는 이 프로젝트의 AI 시스템 아키텍트이자 개발 파트너다.
이미 동작하는 코드베이스 위에 **판단 축적 레이어**를 조각 단위로 얹고 있다.

**이번 요청의 구현 범위는 아래 §3 한 조각뿐이다.** 그 밖의 것(User Rule, Prompt
버전 관리, 벤치마크, 진보성 판단)은 **설계도 하지 말고 언급도 하지 마라.** 지난번에
범위를 넓게 잡아 토큰이 소진되어 중단됐다. 이번에는 하나를 끝내는 것이 목표다.

**검색 단계는 이번에 건드리지 않는다.** 네가 앞서 권한 개발 순서(1. 구성대비 수정과
이력 저장 → 2. 확정 사례·규칙을 다음 분석에 제공 → 3. 확정 결과로 보고서 생성 →
4. 검색 전략으로 확대)에서 이번 조각은 **1번**이다. 보고서 생성 쪽을 먼저 세우고,
검색 판단 축적은 그 흐름의 효과를 확인한 뒤로 미룬다.

작업 순서:

1. 먼저 **구현 계획**을 제시하고 멈춰라. (파일 목록 + 순서 + 각 단계의 산출물)
2. 내가 승인하면 구현한다.
3. 도중에 예산이 부족할 것 같으면 **임의로 축약하지 말고** 어디까지 했고 무엇이
   남았는지 명시하고 멈춰라. 반쪽짜리 배선보다 중단이 낫다.

## 1. 1차 조각에서 완료된 것 (참고, 다시 만들지 마라)

**정답 라이브러리** — 과거 정답 보고서를 판단 사례로 축적해 새 실행에 주입한다.

- 테이블: `answer_cases` / `answer_revisions` / `answer_extractions` /
  `report_context_snapshots`
- 등록(PDF·TXT·MD 또는 기존 실행 결과) → 기존 CLI 프로바이더로 AI 정리(도구 금지,
  예산 3중 게이트, 취소·복구 가능) → 사람이 검수·수정 → 확정 시 불변 리비전 스냅샷
- **근거 검증:** AI가 뽑은 `report_quote`가 정답 보고서 원문에 실제 존재하는지
  대조하고, `source_quote`는 연결 선행문헌 원문에서 확인한다. 없으면 거부
- 주입: 한국어 문자 bigram lexical 랭킹, 토큰 예산 6,000 / 최대 5건, 자기참조 차단,
  실행마다 `ReportContextSnapshot`에 실제 주입 내역 기록
- 화면: 정답 라이브러리 페이지, 실행 화면 토글 + 주입 내역 표시

이때 정의된 `Example` 스키마가 이번 조각과 직접 충돌한다. §4.3을 보라.

```
Example = element / issue / judgment / reason / report_quote /
          source_id / source_quote / location
```

## 2. 반드시 알아야 할 기존 계약 — 이번 조각의 전제

**이 절을 읽지 않고 설계하면 반드시 기존 구조와 충돌한다.**

### 2.1 구성별 분석 블록 — 이미 구성요소 분해가 존재한다

분석 프롬프트가 보고서 끝에 전용 블록을 출력하고, PRISM이 파싱·검증해
`execution_jobs.analysis_manifest` (JSON)에 저장한다. Markdown을 정규식으로 재해석
하지 않는다는 것이 확립된 원칙이다.

```
[PRISM_COMPONENT_ANALYSIS_V1]
{"items": [...]}
[/PRISM_COMPONENT_ANALYSIS_V1]
```

검증 후 저장되는 item 하나의 형태 (`app/analysis_manifest.py`):

| 필드 | 내용 |
|---|---|
| `id` | `C001` 형식. **모델이 적는 것이 아니라 저장 순서로 PRISM이 붙인다** |
| `claim` | 청구항 표시 |
| `symbol` | 구성 기호 |
| `feature` | 구성 내용 |
| `similarity` | 0~100 정수 또는 null |
| `status` | `matched` / `below_threshold` / `not_found` / `unreadable` |
| `difference` | 차이점 서술 |
| `basis` | `direct`(문헌 문언으로 직접 확인) / `inferred`(기재로부터 추론) / 빈 값(표시 안 함) |
| `search_eligible` | `not_found` 이거나 유사도가 기준값 미만이면 true |

상태와 유사도의 정합성(예: `matched`인데 유사도가 기준 미만이면 거부), 기준값 범위,
항목 수 상한(300), 텍스트 길이 상한(4,000)까지 파서가 강제한다.

`analysis_completeness.py`가 이 매니페스트로 분석 누락을 판정하고,
프론트 `AnalysisDegreeOverview`가 표시하며, 「미대응 구성 검색」이 `search_eligible`을
입력으로 쓴다. **즉 이 구조는 이미 세 곳에서 소비 중이다.**

### 2.2 문헌 매핑 블록 — 문헌 식별 방식

```
[PRISM_CITATION_MAPPING_V1]
{"items": [{"citation_number": 1, "attachment": "ATT-02",
            "document_number": "KR10-1234567"}]}
[/PRISM_CITATION_MAPPING_V1]
```

**모델에게 UUID나 sha256을 옮겨 적게 하지 않는다.** PRISM이 첨부마다 `ATT-01` 같은
짧은 별칭을 붙여 보여주고, 모델은 그 별칭만 쓴다. 실제 `attachment_id`와 `sha256`은
PRISM이 자기 기록에서 채운다. 이번 조각에서도 이 규칙을 따라야 한다.

### 2.3 근거 passage 기계

`app/retrieval/evidence.py`가 이미 문헌에서 근거를 뽑아 `page`(페이지 번호)와
`snippet`(원문 구절)을 가진 항목으로 구성한다. passage 앵커링을 새로 발명하지 마라.

### 2.4 보고서 등급 어휘 — **세 번째 어휘를 만들지 마라**

분석 프롬프트의 등급표:

```
95~100%: 동일 대응 🔵   80~94%: 실질 대응 🟢
1~79%:  부분 대응 🟡   0%:     대응 없음 ⚪
```

`report_symbols.py`가 보고서 본문에 이 심볼을 되살린다(판단은 만들지 않고 표기만).

정리하면 현재 등급 어휘가 이미 **둘** 있다 — 프롬프트의 4등급 표기와
`analysis_manifest.status` 4상태. 여기에 E/I/P/N/U를 그대로 얹으면 **세 번째**가 된다.
§4.1이 이 문제다.

## 3. 이번 조각에서 만들 것

### 3.1 목표

구성요소와 구성-문헌 대응을 **실행 부산물(JSON)에서 독립 엔티티로 승격**하고,
**AI 원본을 보존한 채 사용자가 수정할 수 있게** 하며, 그 차이를
**disagreement 데이터로 남긴다.**

### 3.2 현재의 결정적 결핍

현재 `analysis_manifest.items`는 **구성 × (분석 전체)** 의 2항 구조다.
필요한 것은 **구성 × 문헌 × 근거 passage** 의 3항 구조다.

item에는 어느 문헌이 그 구성을 개시했는지가 **없다.** `difference` 서술문 안에
자연어로 섞여 있을 뿐이다. 문헌 매핑 블록(§2.2)은 별도로 존재하지만 구성과 이어져
있지 않다. 그래서 지금은 아래 질문에 기계적으로 답할 수 없다.

> C3는 어느 문헌의 어느 문단으로 개시되었고, 그 판단의 근거 구절은 무엇인가?

또한 청구항은 여전히 `execution_jobs.claim_text` **통짜 텍스트 한 칸**이고,
구성 분해 결과는 실행마다 새로 생기며 **사용자가 편집할 수 없고 실행 간에 재사용되지
않는다.**

### 3.3 요구사항

1. **ClaimElement를 영속 엔티티로. 단, 분해는 AI가 하지 않는다.**
   **구성요소 분해는 사용자가 직접 해서 입력한다.** 현재도 그렇게 쓰고 있다 —
   `claim_text` 칸에 `C1 …` / `C2 …` 형태로 사용자가 적어 넣는다. 따라서 이 조각에서
   ClaimElement는 **AI의 분해 결과를 사람이 고치는 것이 아니라, 사용자가 적은 분해를
   파싱해 보존·재사용하는 것**이다. AI에게 재분해를 시키지 마라.
   필요한 것은: 사용자가 적은 구성이 실행을 넘어 살아남고, 후속 실행이 같은 구성을
   물려받으며, 각 구성에 대응 결과를 매달 수 있게 하는 것.
2. **ElementMapping = 구성 × 문헌 × 근거.** 상태, 근거 passage(문헌·위치·원문 구절),
   판단이유를 가진다.
3. **AI 원본 불변.** 사용자 수정은 덮어쓰기가 아니라 새 레코드다. 1차 조각의
   `AnswerRevision` append-only 패턴을 따르라.
4. **Disagreement 기록.** AI가 무엇이라 했고 사용자가 무엇으로 바꿨는지, 어느
   필드가 바뀌었는지가 **질의 가능**해야 한다.
5. **오류 유형과 짧은 이유를 이번에 함께 만든다.** 네가 앞선 검토에서 개발 1단계로
   "AI 원본, 사용자 확정본, 근거 구절, **오류 유형, 짧은 이유**를 함께 저장"할 것을
   권했다. 나중에 태깅하면 수정 시점의 맥락이 사라져 다시 붙일 수 없으므로 이번에
   같이 넣는다. 매번 긴 글을 쓰지 않도록 **유형 선택 + 짧은 자유입력** 형태여야 한다.
   유형 예시: 구성요소 누락 / 기능 차이 / 구성요소 간 관계 차이 / 실시예 혼합 /
   용어 과대해석 / 용어 과소해석 / implicit disclosure 오판 / passage 오인 /
   날짜·우선권 문제 / 기타.
   (다만 이 데이터로 Rule을 추출하는 기능은 이번 범위가 아니다. 저장까지만 한다.)
6. **미검토와 승인의 구별은 두되, 추가 클릭을 요구하지 마라.**
   사용자가 고치지 않은 칸은 실제로 AI 판단에 동의한 경우가 많다. 그러므로 칸마다
   "확인했다"를 누르게 만드는 설계는 받아들이지 않는다.
   대신 상태는 **미검토 / 확인함 / 수정함** 세 가지로 두고, 사용자가 그 실행의 결과를
   **확정(승인)하는 순간 남아 있던 미검토 칸을 일괄 "확인함"으로 승격**하라.
   추가 조작 비용은 0이면서, "아직 확정하지 않은 실행의 칸"과 "사용자가 승인한 칸"이
   데이터에서 갈린다. 나중에 일치율을 재거나 학습 신호로 쓸 때 확정 전 상태가 정답으로
   섞여 들어가지 않게 하는 것이 목적이다.
7. **"어떤 근거가 있었다면 달리 판단했을 것인가"를 짧게 기록할 수 있어야 한다.**
   선택 입력이다. 강제하지 마라.
8. **재검토 표시(staleness).** 청구항이나 구성 분해가 바뀌면 그에 딸린 기존 대응은
   **재검토 대상으로 표시**되어야 한다. 조용히 유효한 것처럼 남아 있으면 안 된다.
9. **근거 검증.** 1차 조각처럼, 사용자·AI가 제시한 근거 구절이 해당 문헌 원문에
   실제로 존재하는지 대조하라. 존재하지 않는 인용은 저장되지 않아야 한다.
10. **화면.** 구성 × 문헌 행렬을 보고 각 칸의 상태·근거·이유를 수정하는 화면.
    실행 결과 화면에서 이어서 들어갈 수 있어야 한다. 수정 비용이 크면 시스템 전체가
    죽는다 — 유형 선택과 확인 동작은 클릭 한 번으로 끝나야 한다.

## 4. 내가 답을 원하는 설계 결정 — 각각 권고 하나로 답하라

### 4.1 상태 어휘를 어떻게 할 것인가 (가장 중요)

내가 원래 쓰려던 값:

```
E = Explicit disclosure   I = Inherent disclosure   P = Partial
N = Not disclosed         U = Uncertain
```

기존 값 (`status` × `basis`):

```
matched / below_threshold / not_found / unreadable
     ×   direct / inferred / (빈 값)
```

대응 관계를 보면 상당 부분 겹친다.

| 내 값 | 기존 조합 |
|---|---|
| E | `matched` + `basis=direct` |
| I | `matched` + `basis=inferred` |
| P | `below_threshold` |
| N | `not_found` |
| U | ??? |

`unreadable`은 "문헌을 읽지 못했다"이지 "판단이 불확실하다"가 아니다. 그리고 기존
코드에는 **"문헌 판독 제한은 구성이 없다는 뜻이 아니므로 검색 대상으로 올리지
않는다"** 는 명시적 원칙이 박혀 있다. U와 `unreadable`을 같은 칸에 넣으면 이 원칙이
깨진다.

답해야 할 것:

- 새 enum을 도입할 것인가, 기존 `status` × `basis` 조합을 정식 어휘로 승격할 것인가,
  아니면 표시 계층에서만 E/I/P/N/U로 렌더링할 것인가?
- `U`(판단 불확실)를 별도 상태로 둘 것인가? 둔다면 `unreadable`과 어떻게 구별하며,
  `search_eligible` 계산에 어떤 영향을 주는가?
- 기존 유사도 점수(0~100)는 유지할 것인가? 상태와 점수를 둘 다 두면 정합성 검증을
  계속 해야 한다. 점수를 버리면 「미대응 구성 검색」의 기준값 로직이 깨진다.

참고로 너는 앞선 검토에서 **"E/I/P/N/U 방식은 방향에 도움이 되지만 상태값만 바꿔서는
부족하고 판단 대상과 근거를 함께 구조화해야 한다"** 고 했고, **"검색 실패·원문 접근
실패·일부만 검토한 상태를 모두 N으로 저장하면 잘못된 학습 신호가 된다"** 며
`not_found`와 `unreadable`의 구별을 살리라고 했다. 그 입장과 일관되게 답하라.

### 4.2 기존 실행 데이터를 어떻게 할 것인가

이미 쌓인 실행들의 `analysis_manifest`를 정식 테이블로 승격할 것인가, 아니면 새
실행부터만 적용하고 과거는 JSON으로 남길 것인가? 승격한다면 문헌 연결 정보가 없는
과거 데이터를 어떻게 처리하는가?

`analysis_manifest`를 소비하는 기존 세 지점(완결성 판정, 프론트 표시, 미대응 구성
검색)이 깨지지 않아야 한다.

### 4.3 정답 라이브러리 `Example`과 통합할 것인가

1차 조각의 `Example`은 사실상 ElementMapping의 축소판이다 —
`element` / `judgment` / `reason` / `source_quote` / `location`.

이 둘을 하나의 스키마로 합칠 것인가, 별개로 둘 것인가?

- 합치면: 과거 사건의 판단과 진행 중 사건의 판단이 같은 형태가 되어 나중에 학습
  데이터로 묶기 쉽다. 대신 1차 조각을 다시 건드려야 한다 (이미 동작 중이고 테스트가
  붙어 있다).
- 나누면: 1차 조각을 안 건드린다. 대신 나중에 두 스키마를 합치는 비용이 생긴다.

**이 질문에 명확한 권고를 내고, 합치는 쪽이라면 마이그레이션 비용을 구체적으로 적어라.**

### 4.4 AI가 구성-문헌 대응을 어떻게 출력하게 할 것인가

기존 블록 프로토콜(§2.1, §2.2)을 확장할 것인가, 새 블록을 추가할 것인가?
모델에게 `ATT-01` 별칭 규칙(§2.2)을 유지하면서 구성×문헌 대응을 적게 하려면 출력
형식이 어떻게 되어야 하는가? 항목 수가 구성 N × 문헌 M으로 늘어나는데 출력 예산
문제는 어떻게 다루는가?

### 4.5 근거 passage를 어떻게 앵커링할 것인가

문단번호(`[0032]`)인가, 페이지 번호인가, 원문 구절 그대로인가, 문자 오프셋인가?
`evidence.py`가 이미 `page` + `snippet`을 만든다(§2.3). 문헌이 재처리되어도 앵커가
유지되어야 하는가, 아니면 스냅샷으로 충분한가?

## 5. 제약 조건 (1차 조각과 동일, 계속 유효)

1. **1인 사용, 로컬 실행.** 멀티테넌시·인증·RBAC 불필요. `user_id`도 근거 없이 넣지 마라.
2. **SQLite 유지, Alembic 없음.** 1차 조각은 additive 테이블 추가 + 첫 설치 전 자동
   백업으로 해결했다. 같은 방식을 따르되, 기존 테이블 컬럼 변경이 필요하면 명시하라.
3. **Vector DB 추가 금지.** 1차 조각은 한국어 bigram lexical 랭킹으로 해결했다.
4. **LLM 호출은 기존 CLI 프로바이더 경유.** 예산 게이트·취소·복구 패턴을 따르라.
5. **manifest 원칙 유지.** 실행 시점 값을 스냅샷하고, 실패하면 사유를 남긴다.
   `*_error` 칸 관행을 지켜라.
6. **보고서 Markdown을 정규식으로 해석하지 마라.** 버전 붙은 전용 블록만 쓴다.
7. **기존 테스트가 깨지면 안 된다.** 백엔드 pytest 전체와 프론트 vitest 94개가 현재
   모두 통과한다. 이 상태를 유지하고, 새 기능에는 테스트를 붙여라.
8. **점진적 도입.** 기존 실행 이력과 동작 중인 파이프라인을 죽이지 않아야 한다.

## 6. 설계 원칙 (타협 불가)

- LLM의 결론보다 evidence를 우선한다.
- AI의 원본 판단을 덮어쓰지 않는다.
- AI 판단과 사용자 최종 판단을 모두 보존한다.
- 모든 중요한 판단은 관련 문헌과 passage까지 추적 가능해야 한다.
- 사용자의 수정 행동 자체를 학습 데이터로 만든다.
- 최종 판단권은 사용자에게 있다.
