## 원인

### 1. 검색식과 결과량의 균형이 좋지 않았다

모델은 최초 404를 CQL 구문 오류로 설명했다. 그러나 도구는 정상적인 0건 응답으로 반환했고 backend는 `no_results`를 처리하는 경로가 있다. 로그만으로 구문 오류라고 확정할 근거는 없다.

### 2. 자동 재검증이 기존 자료를 다시 조회했다

`search_followup.py:24` 이후 품질 검사에서 미확인 항목이 있으면 추가 실행을 시작한다. 실제 두 후보 모두 `applicant_mismatch`, `support_unverified`, 미확인 대응 1개가 감지됐다.

- 출원인: 모델이 `[CN]`/`[US]`를 생략하고 이름 표기를 재구성했다. `search_verification.py:174` 부근은 정규화한 전체 문자열을 비교하므로 불일치가 됐다. 이 사례에서 다른 회사라는 근거는 없다.
- 대응 근거: 한 후보는 원문과 다른 문구, 다른 후보는 `...`로 축약한 문구를 사용했다. 원문 부분 문자열 검증에서 실패했다. 인용 검증 자체는 필요한 검사다.
- 추가 요청은 원래 프롬프트와 이전 후보 JSON, 미확인 항목을 전달하지만 이전 MCP 응답 본문을 전달하지 않는다.
- 추가 요청의 `already_read_urls`는 실제로 `[]`였다. 이미 성공한 MCP fetch가 있었지만 이 목록에 반영되지 않았다.
- 그 결과 수정할 표기·인용을 기존 증거로 대조하는 대신 같은 문헌의 서지·초록·청구항 전체를 다시 받았다.

## 개선 우선순위

1. 취소·시간 초과에도 초기 후보를 미검증 부분 결과로 유지하고, 확인된 usage는 부분 집계로 보존한다.
2. 추가 검증에 기존 MCP 응답/근거를 전달한다. 동일 식별자·constituent의 재조회는 재사용 가능한 응답이 없거나 실패했을 때만 한다.
3. 출원인 표기 검사는 국가 표기와 복수 표기를 구조적으로 비교한다. 인용은 기존 원문에서 수정하도록 하고, 축약된 문장을 검증 성공으로 통과시키지 않는다.
4. 탐색 응답은 제목·식별자·짧은 관련 초록 등으로 줄이고, 상세·다국어 전문은 유력 후보만 조회한다. 검색 원본은 계속 보존한다.
5. 독립적인 `atlas`처럼 중의적인 넓은 용어보다 메시 병합의 처리 관계가 유지되는 검색식을 우선한다.

## 후속 수정 및 검증

사용자 수정 요청에 따라 다음 변경을 구현했다.

- 자동 재검증에 이미 대조한 원문·evidence_ref와 MCP 문헌 URL을 전달한다. 동일 근거는 중복 전달하지 않고, 필드당 6천 자·전체 본문 6만 자로 제한하며 잘린 자료는 표시한다.
- 같은 실행에서 성공한 상세 조회를 MCP 프로세스가 재시작되어도 재사용한다. 실패, 빈 결과, 식별 불일치, 다른 constituent는 재사용하지 않는다. 재사용 호출도 호출 예산에 포함한다.
- 검색 응답은 주요 서지 및 한 언어 초록으로 축약하고 상세 조회는 기존 한도를 유지한다. 원본 증거 저장은 유지한다.
- 국가 코드 및 줄바꿈/세미콜론 차이만 있는 출원인 표기는 일치로 처리한다. 다른 회사나 누락된 이름, 원문과 다른 인용은 계속 미검증으로 처리한다.
- 재검증 취소·시간 초과 시 최초 완료 단계 후보를 미완료 부분 결과로 보존한다. 성공 상태로 바꾸지 않는다.
- 알려진 단계의 usage를 보존하고 후속 단계의 사용량 누락 여부를 보고서·화면에 표시한다.
- 검색 지시에 중의적 단어 단독 OR 확장을 피하고, 소수 탐색 결과부터 확인하도록 추가했다.

검증: 관련 백엔드 270개 테스트 통과(신규 회귀 8개 포함), 검색 결과 화면 11개 테스트 통과, 프런트엔드 빌드 성공. 실제 보존된 12,621건 질의의 20건 응답을 새 형식으로 변환했을 때 JSON 크기는 123,221자에서 54,365자로 약 56% 감소했다. 이는 응답 크기 비교이며 실제 모델 토큰/시간 절감률은 아니다. 실제 외부 검색·모델 재실행은 하지 않았다.
