# 청구항 입력 후 검색 시작 버튼 비활성화

## 확인된 원인

- 실행 중인 서버의 `/api/settings`에서 검색 도구는 Codex였다.
- `/api/providers`는 npm의 `codex.cmd`를 찾았으나 `--version` 실행이 `node`를 찾지 못해 exit code 1로 실패했다. `executable_ok=false`, `auth_state=UNKNOWN`, `usable=false`였다.
- RunPage의 `!selectedProvider?.usable` 조건이 시작 버튼을 차단했다. 청구항 입력이나 검색 후보 저장 단계에 도달하기 전의 문제다.
- 화면에는 이 조건의 실패 사유가 없었고, 도구 상태도 화면을 처음 열 때만 읽었다.
- 서버가 어떤 경로로 시작되어 Node 경로를 잃었는지는 확정하지 않았다. 현재 셸에서는 Node가 검색되므로 셸의 정상 상태만으로 서버 환경을 판단하면 안 된다.

## 조치

- 설치된 공식 npm 패키지 내부의 `codex.exe`에 대해 버전과 로그인 상태를 먼저 확인했다. Codex 0.149.0, ChatGPT 로그인 정상.
- 기존 다른 도구 경로를 보존하면서 설정 API로 Codex 경로만 해당 실행 파일로 지정했다. 서버 재시작 없이 `executable_ok=true`, `auth_state=OK`, `usable=true`를 확인했다.
- 기본 탐색도 Windows Codex에 한해 npm 내부 네이티브 실행 파일을 cmd 래퍼보다 우선한다. 명시한 사용자 경로와 PATH의 직접 실행 파일 우선순위는 유지한다.
- 실행 불가 사유와 ‘실행 도구 다시 확인’을 시작 버튼 앞에 표시한다. 재확인은 입력 내용을 보존하며 모델을 호출하지 않는다.

## 검증

- 백엔드 resolver/provider 관련 89개 테스트 통과.
- RunPage 렌더링 테스트 10개 통과. 청구항이 있어도 실패한 도구는 차단하고, 재점검 성공 후 같은 청구항으로 시작 버튼이 활성화되는 경우 포함.
- 프론트엔드 TypeScript 검사 및 production 빌드 성공.
- 실행 중인 서버에 연결한 별도 브라우저 탭에서 예시 청구항 입력 후 검색 시작 버튼 활성화를 확인했다. 실제 검색 작업은 생성하지 않았다.

현재 열린 화면은 이전 점검 결과를 들고 있을 수 있다. 다른 메뉴에 갔다가 검색 화면으로 돌아오면 최신 도구 상태를 읽는다. 새로고침하면 새 오류 안내 UI도 적용된다.
