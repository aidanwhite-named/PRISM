## 코드와 로그로 확인한 원인

1. **동사 형태 하나가 필수 검색 조건이 된다.** `search_engine/sources.py::Sources.search`는 자연어 질의의 최대 10단어를 EPO `all` 조건으로 전달한다. 원문의 `receiving`과 모델의 `receive` 차이가 이 실험에서 2건과 0건을 갈랐다. 단어를 무조건 많이 포함하는 방식은 적합하지 않다.
2. **넓은 검색의 첫 페이지만 수집한다.** 최근 실행의 `immersive video rendering`은 172건 중 20건만 가져왔고 공개일은 2026-02-17~2026-09-03에 치우쳤다. 다른 확장 질의는 17,663~25,497건 중 최근 20건만 가져왔다. 대상 KR은 2025년, EP는 2024년 공개다. 초기 결과가 최신순에 치우쳤는데 관련성 순위로 재요청하거나 기간·분류·관계 조합으로 보완하지 못했다. 후보 pool 200은 실제 수집된 후보의 상한일 뿐, 전체 검색 hit를 모두 정렬한다는 뜻이 아니다.
3. **특허와 논문 출처를 구성별로 교대한다.** `Engine.discover/expand`에서 B와 D는 주로 OpenAlex에 배정됐고 EPO의 핵심 구성 질의 A/C는 0건이었다. 모든 구성이 특허·논문 양쪽에서 충분히 시도됐다고 볼 수 없다.
4. **논문·일반 분야 후보가 있으면 Web 보완이 늦어진다.** `discover`는 전체 candidate pool이 비어 있을 때만 즉시 Web을 실행한다. 이후 `expand`는 구성별 발견 기록과 남은 시간으로 Web 여부를 판단한다. 해당 실행에는 web 조회가 한 번도 없었다. 부분 관련 논문이 발견됐다는 사실이 목표 특허 검색의 충분성을 보장하지 않는데도 확장이 억제됐다.
5. **전문 검색으로 오해한 필드가 있었다.** 기존 코드의 `FIELD_FULLTEXT="txt"` 및 `fulltext=True`는 실제로 OPS 제목·초록·출원인·발명자 검색이다. 청구항·설명 전체 검색이 아니다. [EPO OPS 1.3.20, CQL index catalogue, 144~145쪽](https://link.epo.org/web/searching-for-patents/data/en-ops-v3.2-documentation-version-1.3.20.pdf)에서 확인했다. 이번 수정에서 주석을 바로잡고 새 조회 기록에 실제 `search_scope`를 남긴다. 확보한 전문 안에서 수행하는 BM25 문단 검색은 별도로 존재한다.
6. **패밀리 중복 제거와 패밀리 확장은 다르다.** 현재는 수집된 후보의 family ID로 묶지만, 강한 EP seed를 발견한 후 한국 대응문헌을 자동으로 가져오는 완전한 family expansion은 없다. 앞선 EP 검색 성공과 KR 공개번호의 직접 검색 성공을 구분해야 한다.

따라서 최신 실행의 문제는 embedding threshold나 마지막 화면의 정렬에서 정답이 탈락한 것이 아니다. **대상 발명이 retrieval candidate pool에 들어오지 않았다.** 위 질의·페이지 편향·출처 배정·확장 조건 문제는 각각 개선해야 한다.

## 이번에 적용한 화면·분류 변경

- 문헌 A/B/C를 **X/Y/Z**로 변경했다. X=전체 구조와 핵심 특징 유사, Y=구조는 다르나 핵심 특징/관계 유사, Z=구조는 유사하나 핵심 대응은 부분적이다. 기존 저장 결과는 읽을 때 대응 표기로 표시한다.
- 결과 표시와 새 보고서는 **X → Y → Z → 미분류** 순서다. 같은 분류 안에서는 기존 관련성 순서를 유지한다. 청구항의 구성 A/B/C/D는 바꾸지 않는다. 검색 중 내부 후보 선택을 표시용 분류 순서로 대체하지 않는다.
- 기존 결과에서 C가 B보다 앞선 이유는 `ranking.py::rank`의 검증 점수가 표시 순서에도 그대로 사용됐기 때문이다. 분류는 출력 단계의 별도 정렬 기준으로 반영했다.
- 과거 DB와 실행 원본 파일은 감사 기록으로 보존한다. API가 반환하는 화면용 결과 텍스트도 현재 X/Y/Z 표기로 렌더링한다. 과거 저장 artifact 다운로드는 당시 원본이다.
- 검색 전략은 기본 제공 프롬프트 한 개가 맞다. 검색 깊이는 별도 선택이며 UI 명칭을 **빠른 검색 / 심층 검색 / 정밀 검색**으로 변경했다. 새로운 검색엔진 3개가 아니라 같은 엔진에 서로 다른 시간·조회·원문 확인 예산을 적용한다.

| 현재 설정의 검색 깊이 | 시간 예산 | 질의 상한 | 문헌 확보 시도 상한 |
| --- | ---: | ---: | ---: |
| 빠른 검색 | 45초 | 6 | 3 |
| 심층 검색 | 120초 | 12 | 10 |
| 정밀 검색 | 300초 | 30 | 20 |

실제 모든 단계가 반드시 실행되는 것은 아니며, 충분한 근거·남은 예산·취소 상태에 따라 종료한다. 정밀 검색도 전체 corpus를 빠짐없이 검사하지 않는다. 기본 설정은 심층 검색이다.

## 검색 품질 개선의 다음 우선순위

이번 변경은 분류·표시·진단 범위다. 다음 검색 알고리즘 개선은 아직 적용하지 않았다.

1. 드문 명사·관계 조합을 중심으로 짧은 질의를 만들고, 0건일 때 낮은 식별력의 단어·동사 형태 조건을 완화한다. 테스트 문헌의 정답 번호를 실제 검색에 주입하지 않는다.
2. 핵심 특허 질의에 조회 예산을 확보하고, 논문 결과 수와 특허 검색 성공을 별도로 평가한다.
3. 넓은 첫 페이지의 날짜 편향과 전체 hit를 관찰해 좁은 관계 질의, 페이지·기간 분할 또는 다른 소스를 선택한다. 무조건 Top-K만 늘리지 않는다.
4. 강한 해외 seed에서 한국 대응문헌을 실제 패밀리 조회로 확장한다. 각 국가 문헌의 공개일·청구항 근거는 개별 보존한다.
5. Web 확장을 단순 후보 수가 아닌 핵심 관계의 미확인 상태와 소스별 실패로 결정한다.

`evaluation/search_cases.json`에 사용자 제공 KR/동일 family EP를 평가용 정답으로 기록하고, `청구항 1.` 유무의 두 입력 변형을 보존했다. 이 단일 발명으로 일반적인 Recall 수치를 주장하지 않는다.

검증: 백엔드 관련 테스트 **86개 통과**, 프론트엔드 관련 테스트 **20개 통과**, TypeScript 및 production build 성공. 표시 변경 테스트는 과거 A/B/C와 새 X/Y/Z 혼재, 분류 내 순서 보존, 구성 표기 보존을 확인한다.
