# 검색 요청·근거 참조 오류 수정 및 검증

## 범위

어제 마지막 커밋은 `e86b2b2` (2026-09-15 17:41 KST)이다. 이번 수정 전에
`_validate`, `_query_node`는 이 커밋과 동일했다. 전체 롤백만으로 해결되는 결함은
아니었다. 기존 미커밋 변경과 검색 전략 프롬프트는 보존하고, 이번에는 도구 입력
계약·오류 안내·근거 연결만 수정했다.

## 확인된 실패와 수정

- 실행 `cd56908b-d243-4507-a673-895761e9e782`에서 EPO 호출 4회 모두 실패했다.
  2회는 `query.group` 포장을 추가한 잘못된 구조였고, 나머지는 `max_results=30`이었다.
  기존 도구 스키마는 query를 자유 객체로 노출했다. 이제 실제 term/group/date_range
  구조, 필드와 연산자, 배열 및 중첩 한도를 명시한다.
- 잘못된 입력은 계속 네트워크 전에 거절한다. 오류에는 인자의 경로, 허용 범위,
  올바른 호출 예와 재시도 방법을 넣는다. 기술 검색어를 자동 치환하거나 결과 수를
  조용히 줄이지 않는다. 실패와 재시도는 각각 기존 호출 예산에 포함된다.
- 모델이 반환받은 `page_claims` 참조를 `records/0/fields/page_claims`로 다시 쓰는
  오류가 있었다. 해당 문헌에 실제 전달된 응답의 같은 레코드·필드이며 artifact와
  profile도 동일하고 연결이 유일한 경우만 원래 참조로 연결한다.
- 원래 모델 참조는 유지하고 `evidence_ref_resolution`에 연결 기록을 남긴다.
  보존 원문 무결성과 연속 발췌 일치 검사는 그대로 수행한다. 다른 문헌·artifact·
  profile·레코드, 미전달 자료, 변조된 원문, 의역·생략 발췌는 검증 통과하지 못한다.
  화면과 Markdown 보고서에 참조 연결 사실을 표시한다.

## 보존 기록 재검증

이 비교는 새 검색이 아니다. 동일한 원출력·도구 응답·보존 원문에 이번 수정 전후
검증기를 적용했다. 기존 실행 이력과 보고서는 덮어쓰지 않았다.

| 실행 ID 앞부분 | 후보 수 | 근거 확인 대응 행: 수정 전 → 후 | 후보 전체 검증: 수정 전 → 후 |
| --- | ---: | ---: | ---: |
| cd56908b | 8 | 0/14 → 7/14 | 0/8 → 2/8 |
| 71854c3e | 7 | 7/11 → 7/11 | 1/7 → 1/7 |
| 981127b8 | 5 | 0/9 → 0/9 | 0/5 → 0/5 |
| 32ec2292 | 7 | 7/7 → 7/7 | 0/7 → 0/7 |

최신 실행의 직접 발췌 확인 행은 0/14에서 10/14로 늘었다. 근거 문장과 직접
발췌는 서로 다른 필드이며, 문헌 전체 검증에는 서지 충돌 등 다른 조건도 포함된다.
이 숫자는 기술적 관련성이나 검색 누락률이 개선됐다는 뜻이 아니다.

## 검증 방법

검색 입력, 원문 무결성·식별자·발췌 대조, 검색 API와 프롬프트 조립에 대한 관련
회귀 테스트를 실행했다. 프론트엔드 검색 결과 테스트 및 TypeScript/Vite 빌드도
통과했다. 결과 수 초과를 정상 요청으로 재시도하는 회귀와 근거 연결의 부정 사례를
추가했다.

실제 검색은 실행 중인 앱과 분리된 진단 프로세스에서 실행한다. 보존된 사용자
메시지·모델·추론강도·총 호출/시간 예산을 사용하며, 새 시스템의 근거 전달 안내와
도구 스키마를 적용한다. 별도 후속 인용 보완 단계는 실행하지 않는다.

```powershell
cd D:\develope\ARIA\backend
.\.venv\Scripts\python.exe scripts/validate_search_recovery.py <원본 실행 폴더> --live
```

출력은 `%LOCALAPPDATA%\PRISM\diagnostics\search-recovery-*`의 `summary.json`,
`search_manifest.json`, `result.md`에 남는다. 단일 실제 재실행은 모델·외부 검색 결과의
변동이 있으므로 어제 버전 대비 재현율 우위를 확정하는 벤치마크로 해석하지 않는다.

## 실제 재실행 결과

진단 폴더: `search-recovery-20260916T020126087777`.
모델 `gpt-5.6-luna`, 추론강도 `medium`, 총 도구 40회, 제한시간 900초.
보존된 사용자 메시지를 그대로 사용했고 실행은 정상 종료했다.

- EPO: 10회 중 7회 정상 응답. 처음 3회는 `max_results=25`로 실패했지만,
  새 오류 안내를 받은 뒤 20으로 고쳐 재시도했다. `query.group` 형식 오류는 없었다.
  최초 두 질의는 같은 검색어로 재시도했고 0건을 정상 반환했다.
  다른 질의는 206건·1건·50건·8건·91건을 반환했다(전체 결과 수이며 읽은 건수와 다름).
- 후보 10건, 대응 행 15개 중 근거 문장 확인 2개, 문헌 전체 검증 완료 0건.
  이번에는 근거 경로가 정상이어도 모델이 청구항 문구를 생략·재작성하거나 줄바꿈을
  제거해 연속 원문과 일치하지 않는 문제가 확인됐다. 모든 미검증 발췌가 허위라는
  뜻은 아니다. 개행 차이와 실제 문구 삭제를 구분해야 한다.
- arXiv 시간 초과 1회, Google Patents 404 응답 2회가 있었고 실패로 기록됐다.
- 확인된 입력/출력 토큰은 791,626 / 13,170, 캐시 입력 668,672였다.
  비용과 변동성 때문에 추가 실제 검색은 반복하지 않았다.

이 결과는 요청 오류의 회복 가능성과 기존 참조 오류의 기계적 복구를 보여준다.
검색 품질 전체가 개선됐다는 결론은 내리지 않는다. 다음 검증 대상은 모델이 긴
원문을 다시 쓰는 발췌 전달 방식이다. 이 변경과 검색 전략·모델 변경을 함께 묶으면
개선 원인을 구분하기 어려우므로 분리한다.

운영 서버 재시작 명령은 자동 실행 정책에 의해 차단되어 기존 서버(포트 8765)는
유지했다. 수정 코드는 독립 프로세스에서 검증했으며, 전체 수정 적용에는 기존
PRISM 서버를 종료하고 다시 시작해야 한다. 프론트엔드는 빌드를 완료했다.
