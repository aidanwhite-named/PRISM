# 역할 분담 검토 및 개선 — 2026-10-04

프로그램이 입력·원문·실행·저장을 관리하고, LLM이 검색 전략·기술적 판단·보고서를
담당하는 현재 구조를 유지하면서 아래 사항을 개선했다. 원문을 임의로 축약하거나
의무 검토용 모델 호출을 추가하지 않았다.

## 1. 전체 원문 분석에서도 입력 기준으로 누락 확인

기존 `analysis_completeness.check`는 로컬 검색이 선언한 구성 목록을 기준으로
보고서와 대조했다. 전체 원문 전달에서는 그 목록이 없어 대조가 불가능했다.

이제 입력에 명시된 청구항 번호와 구성 표식도 대조한다. `claim_scope.py`가
청구항 헤더와 줄 시작·세미콜론 뒤의 `(A)`·`[A]`·`(전제부)` 등의 표식을
원문 위치에 연결한다. 표식 목록은 최종 분석 입력에도 전달해 식별자를 유지한다.
모든 표식을 다르게 출력했거나, 종속항을 통째로 생략했거나, 같은 식별자를
중복 출력했을 때도 확인 사항을 남긴다. 보고서 저장과 작업 조회에서 같은 검사를 쓴다.

이 검사는 **식별자의 기록 여부**를 확인한다. 구성 내부의 관계·조건·한정이
실제로 모두 분석됐는지, 인용 구절이 판단을 뒷받침하는지는 보장하지 않는다.
명시적 표식이 없는 청구항을 줄바꿈·쉼표로 임의 분해하지 않으며, 전체 원문
전달에서 그 부분의 자동 대조가 불가능하면 보고서에 한계를 표시한다.
유사도와 기술적 판단은 바꾸지 않는다. 파싱 오류·실행 실패가 있는 결과를
완전한 분석으로 표시하지 않는다.

## 2. 검색 이어가기의 관측 상태 전달과 원문 재사용

기존 후보 목록에 더해 `previous_search_state`로 실제 실행한 질의·조회 인수,
실패 이유, 네이티브 웹 도구의 관측 정보, 확보 자료의 종류와 원문 반환 구간을
전달한다. 원문 본문을 상태 메시지에 반복해 붙이지 않는다. 여러 번 이어가도
앞선 웹 질의와 출처 기록이 남는다.

자료 확보와 모델의 검토 완료를 구분하고, 결과가 없는 질의나 실패를 문헌의
부재로 해석하지 않도록 한다. 질의 재시도와 수정은 계속 모델이 선택한다.
이전 실행의 임의 추측을 미처리 작업으로 새로 만들어 전달하지 않는다.

`source_fetch`는 이어받은 출처 응답의 불변 아티팩트를 이용해 다른 원문 구간을
반환할 수 있다. 원래 조회 URL·section이 같고, 캡처와 원본 바이트의 해시가
확인될 때만 재사용한다. 아티팩트가 없거나 손상됐거나 다른 URL·section이면
실제 출처에서 새로 조회한다. `capture_origin`에 `network`·`local_cache`·
`continuation`을 기록한다. 네트워크 재사용은 동일 본문의 모델 입력 토큰을
자동으로 없애는 기능이 아니다.

## 3. 변경이 없는 검색 결과의 반복 저장 제거

검색 대기 중에는 후보 파일·도구 기록의 변경 정보와 실행 상태를 확인한다.
변경이 없으면 전체 기록 읽기·매니페스트 및 보고서 재생성·파일 및 DB 갱신을
건너뛴다. 새 후보·출처 응답·상태 변경은 다음 확인 때 반영한다. 결과 전달 중
도착한 응답도 다음 확인에서 놓치지 않는다. 종료·시간 제한·취소 때는 마지막
스냅샷을 강제로 저장한다. `persistence`에 갱신 횟수와 생략한 확인 횟수를 남긴다.

저장 전후의 로컬 측정: 후보 130개, 변경 없는 확인 40회와 마지막 종료 저장.

않는다. 전체 검색 속도 또는 검색 품질의 개선량으로 해석하지 않는다.
변경 전 엔진 사본은 측정 재현용 아티팩트이며 실제 실행 경로에 사용하지 않는다.


## 4. 대표 사례의 실제 검색 평가 준비

`validate_autonomous_search.py`에 `--claim-file`과 반복 가능한
`--expected-identifier`를 추가했다. 같은 청구항으로 실행 시간·첫 후보 확보 시간·
모델이 보고한 사용량 및 그 완전성·알려진 문헌의 후보 포함 여부를
`validation_metrics.json`에 기록한다. 사용자 작업 이력은 만들지 않는다.

```powershell
.\.venv\Scripts\python.exe scripts/validate_autonomous_search.py --seconds 90 --claim-file case.txt --expected-identifier EP1234567A1 --expected-identifier 10.1234/example
```

위 식별자는 인수 사용법의 예시다. 실제 비교에는 전문가가 중요 문헌과 근거를
검토한 사례를 써야 한다. 문헌번호 회수율은 저장된 후보의 포함 여부만 측정하며,
기술적 관련성·날짜 적합성·구성 분석의 완전성·인용의 타당성과 별도로 평가한다.
사용량이 일부만 보고됐을 때 이를 완전한 비용으로 취급하지 않는다.

이번 작업에서는 실제 모델 검색 품질의 전후 비교를 실행하지 않았다. 원문
전달량을 줄이는 정책이나 추가 사전 구성 분해 호출은 대표 사례의 품질·비용
비교를 바탕으로 결정해야 한다.
