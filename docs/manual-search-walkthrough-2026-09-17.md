# 직접 검색한 과정과 알고리즘 개선안

## 실험 범위

입력은 사용자의 몰입형 비디오 청구항이다. 이미 정답 공개번호와 EP 대응문헌을 알고 있으므로 **블라인드 평가가 아닌 검색 전략 진단**이다. 첫 검색 질의에는 공개번호·정확한 발명명·출원인·정답 패밀리 번호를 넣지 않았다. 후보가 반환된 뒤에만 그 후보의 식별자를 원문·패밀리 조회에 사용했다. 정답 번호는 결과 평가에만 사용했다.

프로그램의 검색 알고리즘은 이번 턴에 변경하지 않았다. 현재 EPO/OpenAlex/arXiv 어댑터와 별도의 Web 검색, 진단용 EPO family GET 조회로 전략을 비교했다. 아래 과정은 실행한 질의와 관측 결과의 기록이다.

## 1. 청구항에서 검색 단위 선택

원 청구항은 최종 검증 기준으로 그대로 유지했다. 검색에서는 다음 개념과 관계를 나눴다.

| 역할 | 이번 입력의 개념 | 검색에서의 처리 |
| --- | --- | --- |
| 대상 | point cloud | 초기 질의의 공통 표현 |
| 관계 입력 | connectivity information | 식별력이 높은 관계 표현 후보 |
| 중간 결과 | geometry / interpolation | 연결성을 어디에 사용하는지 구분 |
| 최종 결과 | target viewpoint / view rendering | 다른 목적의 연결성 기술과 구분 |
| 맥락 | immersive video | 너무 넓거나 다른 분야로 흐를 때 추가 |
| 일반 동작 | receive / obtain | 원문 검증에는 유지하되 모든 검색 질의의 필수 단어로 강제하지 않음 |

`image`, `receive`, `scene` 등이 불필요한 청구항 구성이라는 뜻은 아니다. 모든 단어를 초기 검색의 AND 조건으로 넣지 않는다는 의미다. `connectivity`의 식별력이 높다는 판단도 이 입력에 대한 작업 가설이며, 모든 분야에 적용할 고정 가중치가 아니다.

## 2. EPO: 단어를 늘리는 것보다 관계 조합 선택이 중요했다

현재 어댑터의 제목·초록 `ta all` 검색을 실제로 실행했다. 최대 20건을 가져왔으며, 표의 대상 순위는 EPO 첫 페이지 기준이다. 첫 페이지에 없다는 것은 전체 결과 집합에 없다는 뜻이 아니다.

| 순서 | 실제 질의 | 전체 hit | 대상 패밀리 | 관측한 효과 |
| --- | --- | ---: | --- | --- |
| 1 | `point cloud connectivity` | 203 | 첫 20건에 없음 | 분야를 좁혔지만 아직 넓고 최신 문헌에 치우침 |
| 2 | `point cloud connectivity geometry` | 9 | **EP4386678A1, 5위** | 관계의 결과인 geometry를 추가해 강한 후보 발견 |
| 3 | `point cloud topology geometry` | 24 | 첫 20건에 없음 | 대체 표현이 원래 질의를 대체하면 정답을 잃을 수 있음 |
| 4 | `point cloud adjacency interpolation` | 0 | 없음 | 그럴듯한 동의어도 실제 색인에서는 성과가 없을 수 있음 |
| 5 | `point cloud geometry view synthesis` | 4 | 없음 | 결과 동작의 대체 표현이 같은 발명을 보장하지 않음 |
| 6 | `point cloud connectivity rendering` | 1 | 없음 | hit가 적어도 좋은 질의라고 단정할 수 없음 |
| 7 | `point cloud surface reconstruction` | 2,302 | 첫 20건에 없음 | 상위 개념은 인접 기술 탐색에 유용하나 초기 정밀도가 낮음 |

질의 2에는 이전 진단의 15분 캐시가 적용됐다. 다른 질의는 캐시가 아니었다. hit와 결과 순위는 해당 응답의 관측값이다. 질의 2는 이전 진단에서 실제 네트워크 호출로도 9건·동일 EP 5위를 확인했다.

이번에 사용한 표현 확장의 구분:

- `connectivity → topology / adjacency`: 가까운 표현을 시험한 별도 검색. 정확한 동의 관계로 가정하지 않는다.
- `geometry interpolation → surface reconstruction`: 범위를 넓힌 검색. 원래 기능과 동일하다고 판정하지 않는다.
- `target viewpoint rendering → view synthesis`: 결과 동작의 대체 표현을 시험한다.
- `receive / receiving`: 이전 진단에서 전자는 0건, 후자는 2건·대상 EP 1위였다. 굴절형 처리나 일반 동작 조건 완화가 필요하다는 실측 근거다.

**원래 검색 결과와 확장 검색 결과를 합집합으로 보존해야 한다.** 확장어로 원래 질의를 덮어쓰지 않는다. 문헌별 발견 질의와 표현 종류도 기록한다.

## 3. Web: 짧은 관계 구문으로 공개문헌을 발견했다

실행한 질의는 다음과 같다. Web 도구가 제공한 결과 순서를 검색엔진 전체의 고정 순위나 전체 hit 수로 해석하지 않았다.

1. `"point cloud" "connectivity" "geometry" "viewpoint"`
2. `"point cloud" "connectivity information" "interpolated"`
3. `"point cloud" "connectivity information" "target viewpoint"`
4. `"point cloud" "surface reconstruction" "view synthesis"`
5. `"point cloud" "connectivity" "geometric primitive"`
6. `"point cloud" "connectivity" "surface reconstruction" "rendering"`

초기 1~2번 검색 묶음과 3번 질의에서 같은 발명의 US 공개문헌 및 인도 공보 사본이 반환됐다. 번호나 정확한 발명명을 검색어로 사용하지 않았다. 검색 결과는 단서로 취급했고, 원문·동일 패밀리 확인은 EPO API로 별도 수행했다.

반면 4번은 Gaussian Splatting, 원격탐사 장면 재구성 등으로 넓어졌다. 이런 결과는 새로운 표현을 얻는 데 도움이 되지만 바로 전체 청구항 대응으로 평가하면 안 된다.

## 4. 강한 seed에서 원문 근거와 새로운 표현 확보

EPO 질의 2의 9건을 대상으로 초록에 `connectivity`, `geometry`, `viewpoint`, `image`, `interpolat`가 포함되는지 살폈다. 이 단순 탐색용 점검으로 **EP4386678A1, NOVEL VIEW GENERATION USING POINT CLOUDS**를 선택했다. 이 점검은 범용 ranking model이나 검증 점수가 아니다.

EPO description을 실제로 확보한 결과:

| 입력 구성 | 확인한 관계 | 문헌 위치 |
| --- | --- | --- |
| A | 해당 뷰포인트의 이미지와 포인트 클라우드 수신 | [0008], [0046] |
| B | 포인트 사이 연결성 정보 획득 | [0008], [0046] |
| C | 포인트 클라우드와 연결성을 사용한 기하구조 보간 | [0008], [0046], [0087] |
| D | 이미지와 보간한 기하구조를 사용한 타겟 뷰 렌더링 | [0008], [0046] |

원문 [0016]에서 **geometric primitive**라는 추가 표현을 발견했다. 이 표현은 입력에 없었으므로 발견 전부터 청구항의 필수 조건으로 넣으면 안 된다. 발견한 표현으로 `point cloud geometric primitive`를 EPO에서 검색하니 86건이 나왔고, Web에서도 관련 특허와 기하 기본요소 추출 논문이 나왔다. 확장어로 주변 기술을 더 찾았다는 결과이지, recall 향상률을 계산할 근거는 아니다.

원문 확보는 약 2.55초였다. 전체 description을 여러 LLM에 반복 입력하지 않았다. 앱에 넣을 때는 같은 위치를 문단 검색으로 추리고, 원문 인용 및 관계 판단을 한 번의 검증 호출로 처리하는 편이 적절하다.

## 5. 해외 seed에서 한국 공개문헌까지 실제 패밀리 추적

검색에서 발견한 EP 번호를 사용해 EPO family 서비스를 GET으로 조회했다. **KR 번호를 조회 조건으로 사용하지 않았다.** HTTP 200, 약 3.11초였으며, 중복 참조를 합치면 7개 공개문헌이 반환됐다.

- EP4386678A1
- WO2024126147A1
- CN120418825A
- **KR20250121108A**
- EP4634862A1
- JP2025539556A
- US20260212588A1

패밀리 ID는 84785323이다. 사용자 제공 한국 공개문헌이 실제 family 응답에 포함됐다. 국가별 청구항의 문언·범위가 모두 동일하다는 뜻은 아니므로 근거와 공개일은 문헌별로 관리해야 한다.

이번에 확인한 경로:

```mermaid
flowchart LR
    A[청구항의 관계 표현] --> B[point cloud connectivity geometry]
    B --> C[EPO 9건]
    C --> D[EP4386678A1 원문 확인]
    D --> E[EPO family 조회]
    E --> F[KR20250121108A]
    D --> G[geometric primitive로 추가 탐색]
```

현재 앱의 검색 도구에는 이 family 호출이 연결돼 있지 않다. 이번에는 기존 EPO 인증·HTTP 클라이언트를 사용한 진단용 읽기 요청으로 시험했다. 응답 XML, 요청 주소, 시간, 관측 사용량을 보존했고 사용량도 앱의 quota 기록에 반영했다.

## 6. 논문에서는 부분 관계를 별도로 찾았다

- OpenAlex `point cloud connectivity meshing`: 25,012건 중 10건 조회. 첫 결과들은 DGCNN, 압축 표준 등으로 넓었다. 이 응답 수를 높은 precision으로 해석할 수 없다.
- arXiv `ti:point AND ti:clouds AND all:connectivity`: 155건 중 10건 조회. **Meshing Point Clouds with Predicted Intrinsic-Extrinsic Ratio Guidance**, arXiv:2007.09267이 3번째로 반환됐다.

이 논문의 [공식 초록](https://arxiv.org/abs/2007.09267)은 기존 점들에 연결성을 추가하고 면을 구성할 점의 삼중항을 예측하는 방법을 설명한다. B/C 관련 기술로 검토할 가치가 있지만, 이 초록만으로 이미지 수신부터 목표 뷰 렌더링까지 전체 흐름이 대응한다고 볼 수 없다. 미확인 구성은 absent로 단정하지 않는다.

원문에서 얻은 `geometric primitive`의 Web 확장은 [기하 기본요소 추출 논문](https://portal.fis.tum.de/en/publications/geometric-primitive-extraction-from-point-clouds-of-construction-/)도 찾았다. 연구기관이 제공하는 초록은 연결된 voxel을 분할한 뒤 기본요소를 추출하는 절차를 설명한다. 이 역시 전체 청구항과 부분 관계를 구분해야 하는 사례다.

## 7. 프로그램에 적용할 알고리즘

### 우선순위 1: 같은 청구항에서 안정적인 짧은 질의 만들기

원문은 보존하고, 검색 계획을 위한 사본에서만 `청구항 1.` 같은 표기를 정규화한다. 의미상 같은 입력에 계획 캐시를 재사용할 수 있게 한다. 원문 span 연결은 유지한다.

한 번의 계획 생성에서 핵심 대상, 관계 입력, 처리, 결과와 소수 대체 표현을 얻는다. 모든 구성 단어를 한 질의의 필수 조건으로 붙이지 않는다. 최초 질의는 예를 들어 전체 흐름 1개, 식별력 높은 관계 조합 2개 정도로 제한하고 나머지는 다음 단계 후보로 둔다. 이 개수는 시작 가설이며 검증으로 조정한다.

### 우선순위 2: 응답을 보고 질의를 바꾸는 제어기

| 관측 | 다음 행동 |
| --- | --- |
| 0건 | 일반 동작의 형태를 바꾸거나 한 조건을 완화한 질의, 대체 표현을 별도 조회 |
| 수백·수천 건, 최근 첫 페이지만 반환 | 관계의 다른 입력·결과를 추가해 좁히기; 필요하면 날짜 구간·페이지·다른 소스로 보완 |
| 소수 후보지만 관계 대응이 약함 | 다른 관계 조합이나 Web을 시도; hit 수만으로 종료하지 않음 |
| 강한 후보 발견 | 먼저 해당 문헌의 관련 문단과 family 조회 |
| 일부 관계만 확인 | 부족한 관계에 다음 검색 예산 배정 |
| 새 질의가 새 문헌·근거를 늘리지 못함 | 그 검색 분기를 종료하고 남은 분기 또는 최종 정리로 이동 |

이 제어는 대부분 API 응답과 기록으로 처리할 수 있다. 매 분기마다 LLM을 호출할 필요는 없다. ‘0건이 아니면 성공’ 또는 ‘논문이 있으면 특허 검색도 충분’이라는 판단은 없앤다.

### 우선순위 3: 소스별 실패와 패밀리 조회 처리

특허 핵심 관계 질의에 별도 예산을 확보한다. 특허 A/C, 논문 B/D처럼 구성 번호로 소스를 번갈아 배정하지 않는다. 소스 특성에 맞는 질의를 쓰되 같은 핵심 관계를 서로 다른 채널에서 찾을 수 있어야 한다.

강한 특허 seed를 얻으면 family 조회를 저비용 후속 작업으로 실행한다. 동일 family ID로 이미 수집된 결과를 묶는 일과, 아직 찾지 못한 국가별 문헌을 가져오는 일을 구분한다.

### 우선순위 4: 확장어의 출처와 역할 보존

확장어마다 `claim_translation`, `alternative_expression`, `broader_operation`, `seed_passage`처럼 어디서 얻었는지 남긴다. 넓은 개념이나 원문에서 얻은 구현예를 원 청구항의 필수 조건으로 승격하지 않는다. 질의별 후보는 합집합으로 유지한다.

### 우선순위 5: 원문과 관계 검증에 LLM 집중

후보 초록·문단은 lexical/BM25와 출처별 순위를 이용해 먼저 줄인다. 최종 검증에 원 청구항 전체, 구성별 관련 문단, 주변 문맥을 제공한다. LLM은 관계·차이와 X/Y/Z를 설명하고, 인용문이 실제 제공 원문에 존재하는지는 프로그램이 확인한다.

초기 탐색에서는 여러 문헌이 서로 다른 구성을 다뤄도 후보로 보존한다. 최종 판정에서는 한 문헌의 서로 다른 관계를 임의로 연결하거나 여러 문헌의 구성을 한 문헌처럼 합치지 않는다.

## 8. 예산과 stopping condition

- Fast: 적은 수의 특허 관계 질의와 필요시 짧은 Web 질의로 seed를 찾고 첫 후보를 표시한다.
- Deep: seed 원문·family, 부족한 관계, 인접 논문을 선택적으로 확인한다.
- 정밀: 미해결 분기와 넓은 결과의 페이지·기간 편향을 더 확인한다.

**정답 찾기 회귀시험**에서는 대상 공개문헌 또는 확인된 패밀리를 찾으면 해당 성공 조건을 충족한다. **실제 선행기술 검색**에서는 한 유사문헌을 찾았다는 이유만으로 충분하다고 종료하지 않는다. 시간·API·토큰 예산, 미해결 관계, 최근 분기의 신규 근거 증가 여부를 함께 보고 종료 이유를 기록해야 한다. 신규성·진보성 판단과도 구분한다.
