# 종속항 보고서의 근거 패키지 생성 실패 진단

2026-09-18 로컬 실행 DB, 실행별 retrieval 기록, 소스를 대조했다. 아래 진단은 수정 전 상태를 설명하며, 사용자 요청에 따라 적용한 변경은 마지막 절에 기록했다.

## 결론

직접 원인은 Codex의 `gpt-5.6-luna`가 검색 2라운드에서 반환한 모델 용량 부족 오류다.

> Selected model is at capacity. Please try a different model.

청구항 구성 분해나 PDF 추출 실패가 아니다. 모델의 순간적인 처리 용량 부족을 일반 `PROCESS_ERROR`로 취급하고, 화면에서는 이를 다시 “근거 패키지를 만들지 못했습니다”로 묶어서 표시한다. 서버 내부의 구체적인 혼잡 원인이나 현재 복구 여부는 이 기록으로 알 수 없다.

## 실행에서 확인한 사실

| 항목 | 관측 |
| --- | --- |
| 실행 ID | `af5183a6-30b0-4a5d-ab4e-58cf995c4fdd` |
| 실행 시각 | 2026-09-18 15:15:07–15:16:48 KST |
| 분석 대상 | 청구항 2–5, `MAPPED` 종속항 추가 분석 |
| 원본 실행 | `52ac01e9-9e56-4eb5-95da-ee1d83c2a9a7` |
| 모델 | `codex / gpt-5.6-luna` |
| PDF 추출 | 5개 문헌, 총 63쪽 모두 `complete` |
| 1라운드 | 정상 응답, 구성 15개 선언, 검색 action 15개 실행 |
| 2라운드 | 약 4.6초 후 `provider_error`, 모델 용량 부족 메시지 |
| 페이지 열람 | `read_pages`로 열람한 페이지 0쪽; 검색 후보 발췌는 이미 수집됨 |
| 결과 | `FAILED / PROCESS_ERROR`, 최종 보고서 생성 단계에 진입하지 못함 |

근거 파일은 `%LOCALAPPDATA%/PRISM/runs/<실행 ID>/retrieval/`의 `retrieval_manifest.json`, `retrieval_trace.jsonl`, `rounds/round-*.in.txt`, `rounds/round-*.out.txt`다. DB의 `execution_events` 29번과 31번에도 같은 용량 부족 메시지가 있다.

`search_budget_exhausted=true`도 기록돼 있지만, 이는 1라운드 반환 예산 때문에 후보를 후속 라운드로 이월한 상태다. 근거 패키지 예산 초과 판정은 실행되지 않았으며 `evidence_budget_limited=false`다. 최종 패키지 크기를 늘리는 것을 이번 장애의 해결책으로 삼을 근거는 없다.

## 원인을 사용자에게 잘못 전달하는 경로

1. `backend/app/providers/codex_stream.py`는 인증 오류와 사용량 제한을 구분하지만 모델 혼잡을 구분하지 않는다.
2. `backend/app/retrieval/agent.py::_abort_reason`는 해당 오류를 `provider_error / PROCESS_ERROR`로 반환한다.
3. `RetrievalAgent.run`은 즉시 종료한다. PRISM 계층의 같은 라운드 자동 재시도가 없다.
4. `backend/app/retrieval/service.py`는 오류가 있으면 패키지 조립을 생략한다.
5. `frontend/src/components/RetrievalManifestView.tsx`는 `retrieval_manifest_error`가 있으면 원인 종류와 무관하게 같은 제목을 보여준다.

검토가 끝나지 않은 후보로 최종 보고서를 강제로 만드는 것은 해결책이 아니다. 중단 자체는 필요하며, 개선 대상은 일시 오류 복구와 원인 표시다.

## 함께 발견한 문제

### 이전 라운드 응답이 실패한 라운드의 출력으로 기록됨

실제 `round-01.out.txt`와 `round-02.out.txt`는 바이트 단위로 동일하다. 각각 7,054자이고 SHA-256도 같다. 공용 `codex_last_message.txt`의 수정 시각은 1라운드 종료 직전인 06:16:41 UTC에 머물러 있다.

모든 라운드는 같은 `rounds` 폴더를 사용한다. `CodexCliProvider.execute`는 CLI가 실패한 뒤에도 그 폴더의 `codex_last_message.txt`를 읽는다. 새 출력이 만들어지지 않으면 이전 응답을 가져오는 구조다. 이번에는 오류 검사에서 멈춰 이전 응답을 검색 action으로 실행하지 않았지만, 감사 기록은 실제 2라운드 응답처럼 보이게 된다.

외부 모델 호출을 모두 모의 처리한 오프라인 재현에서도, 이전 출력 파일이 있는 상태에서 `turn.failed`를 반환하면 `is_error=true`와 이전 `result_text`가 동시에 반환됨을 확인했다. 재현 결과는 `data/validation/dependent-claims-capacity-20260918/reproduction.json`에 저장했다.

### 선행항 원문이 검색 단계에 전달되지 않음

이번 실행 DB에는 선행항 원문 645자가 `prior_claim_text`로 저장돼 있지만 실제 1라운드 입력에는 없다. `execution/runner.py`는 최종 분석 조립에는 `prior_claim_text`를 넘기면서 `run_retrieval`에는 새 `claim_text`만 전달한다. 검색 서비스·에이전트 인터페이스에도 선행항 입력이 없다.

이 문제는 이번 용량 오류의 원인은 아니다. 다만 “제1항에 있어서”, “상기 …”의 의미를 선행항과 연결해서 검색해야 하는 종속항 분석의 품질 문제다. 이미 검색 범위에서 빠진 관련 근거를 최종 보고서 모델이 뒤늦게 회복하기는 어렵다.

## 권장 개선 순서

1. **오류 분류와 안내:** `MODEL_CAPACITY` 같은 원인 코드를 추가하고 `failure_stage`, `retryable`, 원문 오류를 분리해 기록한다. 화면에는 “검색 2단계에서 선택 모델이 혼잡해 중단되었습니다”와 재시도·모델 변경 안내를 표시한다. 계정 사용량 제한과도 구분한다.
2. **출력 파일 격리:** 라운드와 호출 시도마다 별도 출력 경로를 사용하고, 해당 호출에서 생성된 출력만 읽는다. 현재 호출의 실제 부분 출력은 보존하되 이전 호출 파일로 대체하지 않는다. 재시도 기능에 앞서 적용하는 것이 좋다.
3. **같은 라운드의 제한적 재시도:** 명확한 일시 혼잡에만 예를 들어 5초·15초 후 최대 2회 추가 시도한다. 같은 입력·모델·검색 상태를 유지하고 검색 action을 중복 실행하지 않는다. 실패 시도는 검색 라운드와 별도로 기록하고 총 시간·호출 상한 및 취소를 적용한다. 인증, 사용량 소진, 정책 위반에는 같은 재시도를 적용하지 않는다.
4. **종속항 검색 문맥 보완:** `prior_claim_text`를 runner → service → agent → prompt로 전달하고, 새 분석 대상과 선행항 참고 문맥을 별도 필드로 표시한다. 선행항을 새 분석 대상으로 중복 선언하지 않도록 한다. 참고 문맥도 실제 전송 크기와 입력 해시 계산에 포함한다.
5. **중장기 재개 기능:** 구성 상태·검색 후보·이월 요청·열람 기록을 체크포인트로 저장한다. 재개 때 입력·첨부 해시·도구 버전을 검증한다. 다른 모델로 재개할 경우 기존 후보를 다시 검토하게 하고, 모델 변경은 이력에 남긴다. 사용자가 선택하지 않은 모델로 조용히 전환하지 않는다.

우선 1–4를 구현하고, 프로세스 재시작을 넘는 체크포인트 복구는 별도 작업으로 나누는 편이 적절하다.

## 구현 시 확인할 회귀 조건

현재 `pytest tests/test_codex_provider.py tests/test_followup.py -q`는 종료 코드 0으로 통과했다. 기존 테스트가 통과해도 위의 출력 재사용과 검색 문맥 누락을 포착하지 못하므로 다음 사례를 보강해야 한다.

- 혼잡 후 다음 시도 성공: 구성 ID와 기존 검색 기록을 유지하고 실패했던 라운드부터 진행한다.
- 혼잡 지속·취소·전체 시간 초과: 정해진 횟수·시간 안에 끝나고 올바른 원인과 시도 횟수를 남긴다.
- 이전 출력 존재 + 다음 호출 실패: 실패한 호출의 출력에 이전 응답이 섞이지 않는다.
- 선행항 포함 종속항 입력: 검색 입력에 선행항 원문이 존재하고 분석 대상은 새 종속항으로 유지된다.
- 참고 문맥으로 입력 한도 초과: 전송 전에 명확히 판정하며 조용히 내용을 잘라내지 않는다.

## 현재 실행의 복구 방법

완료된 원본 실행에서 “종속항 추가 분석”을 다시 열고 청구항 2–5를 넣어 재실행할 수 있다. 같은 모델은 잠시 뒤 재시도하거나 분석 모델을 변경한다. 원본 실행은 `agy / gemini-3.8-flash-medium`으로 성공한 이력이 있으나 현재 가용성을 보장하는 것은 아니다. 이번 기록만으로 PDF 교체나 패키지 예산 확대를 권할 이유는 없다.

## 적용한 변경

- 명확한 Codex `model is at capacity` 오류를 `MODEL_CAPACITY`로 분리한다. 정상 응답에서 같은 문구를 인용한 경우에는 적용하지 않는다. 화면은 모델 혼잡·사용량 제한·입력 초과 등을 구분하며, 과거 `PROCESS_ERROR`로 저장된 동일 혼잡 메시지도 읽어서 안내한다.
- 검색 라운드에서 모델 혼잡에만 5초·15초 후 최대 두 번 추가 시도한다. 기존 라운드 시간 제한을 모든 시도와 대기가 공유한다. 취소는 대기 중에도 확인하며, 실행 중 제한 시간 초과는 프로세스를 정리한다. 입력·선택 모델·구성·검색 상태는 유지한다. 인증·사용량·도구 정책 오류는 재시도하지 않는다.
- Codex 출력 파일은 호출별 UUID 경로를 사용한다. 검색 호출은 `rounds/round-NN/attempt-NN/`에 격리하고 각 시도의 출력·stdout·stderr를 보존한다. 기존 `round-NN.in.txt`, `.out.txt`는 호환을 위해 유지한다.
- manifest의 라운드에 `attempts`를 추가하고 시도별 원문 오류·사용량·입출력 해시를 기록한다. 실패에는 `failure_stage`, `retryable`, `provider_error`를 기록한다. 기존 `retrieval_rounds` 사용량 구조는 유지하고 별도 `retrieval_attempts`에 모든 호출을 남긴다.
- `prior_claim_text`를 최종 분석뿐 아니라 검색 단계에도 전달한다. JSON의 별도 참고 필드로 전달하고, 구성 분해 대상은 새 `CLAIM_TEXT`로 제한하도록 계약에 명시한다. 선행항은 입력 바이트 검사·라운드 입력 해시·manifest의 `prior_claim_sha256`에 반영한다.

프로세스 재시작 후 검색을 이어가는 체크포인트 복구와 자동 모델 전환은 이번 변경에 포함하지 않는다. 종료된 과거 실행을 자동으로 다시 호출하지도 않는다.

### 수정 후 검증

- 백엔드: 신규 혼잡·출력 격리 테스트와 관련 기존 테스트 합계 253개 통과. 사용량 기록의 호환 구조를 정리한 뒤 혼잡 테스트 13개를 다시 실행해 통과했다.
- 프런트엔드: `RetrievalManifestView.render.test.tsx` 9개 통과, TypeScript 검사와 `npm run build` 통과.
- 실제 API 흐름에서 `MAPPED` 후속 분석의 선행항 참고 원문 전달, 새 분석 대상 유지, 인용발명 번호 보존을 확인했다. 외부 모델 호출은 사용하지 않았다.
- 빌드 산출물은 `frontend/dist`에 반영했다. 로컬 서버 재시작 명령은 도구 실행 정책에서 `blocked by policy`로 거부되어 실행되지 않았다. 백엔드 변경을 사용하려면 실행 중인 PRISM을 종료한 뒤 다시 실행해야 한다.

### 후속 최소 롤백

이후 보고서 품질 저하를 확인하는 과정에서, 위 변경 중 공통 검색 프롬프트에 추가했던 종속항 해석 지시 5줄만 제거했다. 선행항 원문 전달과 혼잡 처리·출력 격리는 유지한다. 검색 시스템 프롬프트는 변경 이전 실행과 동일하다. 적용 범위와 실제 전후 재실행 비교는 [검색 프롬프트 최소 롤백 비교](prompt-rollback-comparison-2026-09-18.md)에 기록한다.
