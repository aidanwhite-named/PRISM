# 검색 중간 저장·질의 수정·청구항 원문 대조

사용자가 제공한 부모/자식 뼈의 연동 관절 한계 청구항으로 기존 검색과 개선 경로를 비교했다. 특정 문헌번호를 검색 로직이나 X 분류 규칙에 넣지 않았다.

## 구현

- 웹 모델이 보고하는 완전한 JSON 후보를 스트림에서 즉시 읽어 `reported_findings.json`, 후보 목록 및 체크포인트에 저장한다. 마지막 JSON이 끊겨도 앞의 완전한 후보는 유지한다. 검색 도구 사용이 관측된 이후의 보고만 받고, 검색어 안의 문헌번호를 후보로 간주하지 않는다. 출처는 `web_reported`이며 원문 검증 전에는 인용 근거가 아니다.
- EPO/OpenAlex의 실제 결과 수, 검색 범위와 후보 초록을 모델에 보내 대체 질의를 만든다. 기존 질의와 후보를 유지하고 변경 이유를 기록한다. 대체 질의도 모두 0건이면 남은 시간·모델 호출 예산 안에서 한 번 더 수정한다.
- OpenAlex 제목·초록 검색을 선택할 수 있게 연결하고, 따옴표·AND/OR/NOT를 보존한다. 이전에 구문을 제거한 결과를 재사용하지 않도록 해당 소스의 캐시 키를 바꿨다. 지원 문법은 [OpenAlex 공식 검색 문서](https://help.openalex.org/api/searching/) 기준이다.
- 수집 단계에서 분류와 원문 대조 시간을 각각 남긴다. 원문 다운로드도 대조 모델 호출에 필요한 시간을 소진하지 못하게 한다.
- 특허는 청구항부터 확보한다. EPO에 원문이 없으면 공개 페이지를 확인하며, Google Patents의 공개번호와 URL이 일치하고 명시적인 claims 섹션이 있는 경우만 청구항으로 추출한다. 일반 웹 페이지를 청구항이나 전문으로 승격하지 않는다.
- 일본어 청구항도 검색어와의 어휘 일치 여부와 무관하게 대조에 넣는다. 문헌별로 대조 문맥을 배분하고 청구항을 특징별로 반복해 넣으면서 후반부 조건을 잘라버리는 문제를 줄였다. 인용은 원문 문자열과 위치를 검증한다.

## 실제 측정

동일한 설정의 agy / `gemini-3.8-flash-medium`으로 실행했다. 단일 실행이며 모델 변동과 캐시 사용이 있으므로 속도 개선율이나 일반 재현율로 해석하지 않는다.

| 실행 | 후보 | 확보한 전문 | 검증된 인용 행 | JP7475618 자동 발견 |
|---|---:|---:|---:|---|
| 기존 exhaustive | 20 | 0 | 0 | 실패 |
| 개선 1차 exhaustive | 29 | 1 | 0 | 실패 |
| 개선 2차 exhaustive | 20 | 1 | 7 | 실패 |
| 최종 deep (120초) | 20 | 1 | 0 | 실패 |

개선 1차는 질의 수정으로 후보가 늘었지만 원문 대조 모델 호출이 시간 초과됐다. 2차는 인용 검증까지 완료했다. 7행 중 5행은 골격 운동학 논문 전문, 2행은 다른 후보의 초록에서 확인됐다. **인용 문자열이 확인됐다는 뜻이며 핵심 한정 D/E가 대응한다는 뜻은 아니다.** 전문을 읽은 골격 운동학 논문은 Z였고, 직접 검색에서 찾았던 핵심 논문들도 아직 자동 발견하지 못했다. 2차의 구문 검색은 0건이었다. 질의 수정은 자동화됐지만 항상 검색 품질을 높인다고 입증되지는 않았다.

2차까지의 웹 탐색은 시간 초과 전에 후보 JSON을 출력하지 않아 웹 후보를 저장하지 못했다. 스트림 저장의 중단 내구성은 회귀 테스트에서 검증했지만, 이 두 실제 실행에서 중간 저장 성공으로 계산하지 않았다. 이후 지시문에서 접근 실패·중계 링크도 미검증 후보로 먼저 보고하도록 보완했다.

최종 deep 재실행(`498fc266-b6ad-4477-b798-fa874521755e`, 115.625초)도 웹 후보 0건이었다. 질의 수정 약 15.8초, 웹 탐색 약 28.2초, 원문 대조 약 26.2초에서 각각 시간 초과됐다. 분류 8건은 완료했고 전문 1건을 확보했으나 인용 검증은 완료하지 못했다. 120초 설정에서 이 모델의 여러 단계를 모두 완료하는 안정성은 확보되지 않았다. 따라서 **검색 품질 개선을 완료했다거나 JP의 자동 발견을 해결했다고 결론내리지 않는다.**

추가 CLI 진단에서 검색 도구 이벤트는 질의·호출 상태만 제공하고 검색 결과 본문을 전달하지 않는 것을 확인했다. 모델이 사용한 Google grounding 중계 URL은 원문 열람 시 차단 페이지/HTTP 파싱 오류가 발생했다. 따라서 검색어와 호출 횟수만 보고 문헌을 찾았다고 처리할 수 없다. 중간 JSON을 출력하지 않는 공급자 동작과 원문 접근 실패는 남은 제약이다. KIPRIS API 오류도 계속되며 키·서비스 승인·한도 중 원인은 응답만으로 특정하지 못했다.

## JP7475618B1 분류 진단

검색 성과와 분류 성능을 분리하기 위해, 공개번호와 URL을 명시적으로 넣은 별도 진단을 실행했다. EPO 청구항·설명 조회는 404였지만 Google Patents에서 해당 공개번호의 청구항을 확보했다.

- 실제 모델 결과: **X**, `retrieved_passages`, `provisional=false`.
- 사용자 청구항의 A–E 모두 `explicit`; 인용 5개 모두 원문 문자열 검사 통과.
- 특히 D의 “하나의 파라미터가 다른 둘 이상의 파라미터 한계에 영향”과 E의 “한계 초과 시 범위 내 보정”을 동일 문헌에서 확인했다.
- 문헌번호별 특별 처리나 X 강제 규칙은 없다. 이는 해당 실행의 기술적 유사성 분류이며 향후 모든 실행의 자동 발견을 보장하지 않는다.
- 진단은 청구항에 표시된 A–E를 그대로 나눈 기본 계획을 사용했다. 자동 검색의 계획 생성과는 별개다.

재현:

```powershell
.\backend\.venv\Scripts\python.exe backend/scripts/diagnose_claim_document.py --case coupled_joint_limits --document-number JP7475618B1 --url https://patents.google.com/patent/JP7475618B1/en --output docs/artifacts/joint-search-comparison-20260917/jp-classification-diagnostic.json
```
