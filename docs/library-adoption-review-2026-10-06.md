# PRISM 외부 라이브러리 도입 검토

검토일: 2026-10-06. 현재 PRISM 코드와 각 프로젝트의 공식 GitHub 저장소·문서·GitHub API를 비교했다. 별점과 릴리즈 정보는 조회 시점의 값이다. 후보를 설치하거나 PRISM의 기능을 변경하지 않았으며, 실제 문헌으로 성능을 비교하는 시험은 아직 수행하지 않았다.

## 판단

도입 가치가 가장 큰 영역은 PDF의 위치 정보와 웹 본문 추출이다. 특허 검색 서비스 연결 자체보다, 확보한 원문을 정확하게 읽고 근거로 연결하는 품질을 우선 개선하는 편이 현재 PRISM에 적합하다.

현재 PRISM은 이미 EPO·KIPRIS·OpenAlex·arXiv 연결, 원문 보관, 검색 이어가기, 요청 제한, 구성별 근거 연결을 갖추고 있다. 다른 특허 검색 프로그램을 통째로 넣으면 기존 기능과 겹칠 수 있다. 확인한 후보 중 전체 검색 시스템을 대체할 만큼 충분한 이점을 확인한 것은 없다.

## 선정 기준

- GitHub 별점은 사용 관심도의 지표로만 사용한다. 정확도나 보안을 보장하는 평점으로 해석하지 않는다.
- 저장소 보관 여부, 최근 릴리즈와 코드 갱신, 테스트 및 자동 테스트 구성, 공식 문서를 함께 확인한다.
- 라이선스와 추가 모델·실행 환경의 요구사항을 확인한다.
- Windows 설치 부담, 기존 원문 검증·페이지·근거 ID 보존, 요청 제한·취소 동작을 검토한다.
- 최종 도입은 PRISM이 실제로 처리하는 특허와 논문에서 비교 시험을 통과하는 조건으로 판단한다.

pdfplumber, Trafilatura, Tenacity, Docling, python-epo-ops-client는 테스트 디렉터리와 GitHub 자동 테스트 구성을 확인했다. 이것은 개발 과정의 근거이며, 현재 PRISM 문헌에서의 정확도 검증이나 해당 테스트가 모두 통과한다는 확인을 대신하지 않는다.

## 1. pdfplumber: 문장 끝 숫자와 읽기 순서 문제에 가장 직접적인 후보

현재 업로드 문서 처리는 `backend/app/ingestion/service.py`에서 pypdf의 `extract_text()`를 사용한다. 검색으로 받은 PDF도 `backend/app/search_engine/source_text.py`에서 같은 방식으로 읽는다. 이후 `backend/app/report_sources.py`가 텍스트를 규칙으로 나눠 문장 ID를 만든다.

pdfplumber는 글자 위치, 크기와 페이지 객체를 제공하고, 영역별 추출·필터링·시각적 확인을 지원한다. 이 정보를 활용하면 본문, 작은 위첨자, 반복 머리말·꼬리말, 단 제목의 경계를 판단할 재료를 얻을 수 있다. [공식 기능 설명](https://github.com/jsvine/pdfplumber#the-pdfplumberpage-class)

PRISM에서는 기존 pypdf 경로와 비교하는 보조 추출기로 먼저 시험하는 것을 권한다. 본문 문장 끝에 붙은 `2.`가 다음 제목 번호인지, 각주인지, 본문 숫자인지는 글자 위치와 주변 문맥을 함께 판단해야 한다. 라이브러리 설치만으로 이 문제가 해결되는 것은 아니다.

장점은 별도 생성형 AI 호출 없이 위치 정보를 얻는다는 점이다. 다만 읽기 순서와 속도가 항상 기존 추출보다 좋다는 보장은 없다. 공식 설명도 스캔 PDF보다 텍스트로 생성된 PDF에 적합하다고 명시한다.

## 2. Trafilatura: 검색한 웹 원문의 불필요한 문구 줄이기

현재 일반 HTML 본문은 `backend/app/search_engine/fetcher.py`의 자체 `ArticleHTML`과 `source_text.py`에서 처리한다. 특허 청구항과 arXiv 본문을 위한 전용 처리도 존재한다.

Trafilatura는 웹페이지에서 본문과 메타데이터를 추출하고 반복 메뉴·머리말·꼬리말 등의 잡음을 줄이는 도구다. [공식 설명](https://github.com/adbar/trafilatura)

권장 적용은 PRISM이 이미 내려받아 보관한 HTML 바이트의 본문 추출이다. 다운로드는 기존 요청 제한·주소 확인·시간 제한 경로를 유지한다. 특허 청구항 전용 파서와 arXiv 전용 파서는 우선 유지한다.

기대 효과는 관련 없는 웹 문구가 근거나 모델 입력에 섞이는 일을 줄이는 것이다. 반대로 도구가 짧은 청구항·표·수식 같은 중요한 부분을 잡음으로 제외할 수도 있다. 추출된 본문을 원본 HTML과 대조하고, 누락 여부를 시험해야 한다. 토큰 절감량은 실제 비교 전에는 확정할 수 없다.

## 3. Tenacity: 재시도 정책 정리

PRISM의 EPO 클라이언트에는 이미 401 인증 갱신, 일시적 HTTP 오류 재시도, 취소 가능한 대기가 구현되어 있다. Tenacity는 동기·비동기 재시도와 대기·중단 조건을 제공하는 일반 도구다. [공식 설명](https://github.com/jd/tenacity)

도입 효과는 요청 실패 처리의 중복을 줄이고 정책을 읽기 쉽게 만드는 데 있다. 특허 검색 정확도를 직접 높이는 도구는 아니다. 기존 코드가 작고 검증되어 있다면 교체 이득이 작다.

전체 검색 제한시간, 사용자 취소, API 요청 사용량 기록을 지키는 조건으로 일부 구간에서만 검토한다. 이미 재시도하는 라이브러리를 다시 감싸 요청 횟수가 늘어나지 않도록 해야 한다.

## 4. Docling: OCR·복잡한 문서 확장을 원할 때

Docling은 PDF 레이아웃·읽기 순서·표·수식과 다양한 문서 형식을 처리하는 도구다. [공식 저장소](https://github.com/docling-project/docling)

현재 PRISM의 텍스트 PDF 지원을 스캔 문서·복잡한 논문으로 확대할 때 후보가 된다. 다만 모델 다운로드·실행 환경·메모리·설치 부담을 실제 Windows 환경에서 측정해야 한다. 코드 라이선스와 사용 모델의 라이선스는 따로 확인해야 한다.

기본 처리 경로 전체를 교체하기보다 사용자가 선택하는 고급 문서 처리 기능으로 시험하는 편이 적합하다. OCR이나 구조화 출력은 검증용 원문과 별도로 보관하고, 페이지와 실제 문장 위치를 함께 연결해야 한다.

## 5. 특허 전용 클라이언트는 무엇을 가져올 수 있나

python-epo-ops-client는 EPO OPS에 접근하는 전용 Python 도구다. 요청 제한을 처리하는 Throttler와 선택적인 Dogpile 캐시를 제공한다. [공식 미들웨어 설명](https://github.com/ip-tools/python-epo-ops-client#middlewares)

그러나 PRISM에도 EPO 인증·요청 제한·재시도·원본 응답 저장이 있다. 이 라이브러리를 붙인다고 검색 결과의 품질이나 한국 특허 검색이 자동으로 개선되는 것은 아니다. 별점 193개는 특허 분야에서는 참고할 수 있으나, 대규모 사용 검증의 증거로 삼기에는 부족하다. 현재는 외부 구현과 기존 EPO 동작을 비교하는 참고 대상으로 판단한다.

patent_client는 특허 데이터 접근 도구였지만 공식 저장소가 보관 처리되어 현재 유지보수하지 않는다고 밝힌다. 유지보수되는 후속 프로젝트를 안내하고 있으나, 후속 프로젝트까지 PRISM 도입 후보로 검증한 것은 아니다. [공식 보관 안내](https://github.com/ParkerHancock/patent_client)

## 현재 사용 중인 라이브러리도 점검할 가치가 있다

PRISM은 arxiv와 pyalex를 이미 사용한다. 따라서 모든 외부 연결이 자체 구현인 것은 아니다. 로컬 검색은 SQLite FTS5를 사용하며, sentence-transformers는 선택 기능이다. 현재 규모에서 외부 검색 서버나 별도 벡터 DB로 옮겨야 할 근거는 이번 검토에서 확인하지 못했다.

pypdf는 현재 `5.2.0`으로 고정되어 있다. [공식 저장소](https://github.com/py-pdf/pypdf)의 조회된 최신 릴리즈는 `6.19.0`이다. 새 라이브러리 비교 전에 현재 pypdf의 최신 버전도 동일 문서로 시험하면 좋은 기준선이 된다. 업그레이드만으로 `2.` 혼입 문제가 해결된다고 가정해서는 안 된다. 기존 인라인 이미지 색공간, 암호화, 페이지 경계와 원문 검증 테스트를 유지해야 한다.

spaCy도 문장 분리 후보로 살펴봤으나, PDF에서 본문과 표식이 섞인 원인을 해결하려면 위치 정보가 먼저 필요하다. 문장 분리만을 위해 지금 전체 NLP 의존성을 추가하는 것은 우선순위가 낮다.

## 적용 순서와 통과 기준

1. pypdf 현 버전·최신 버전·pdfplumber를 같은 문서로 비교한다. 특허 단락, 두 단 논문, 수식, 표, 위첨자·각주, 페이지 경계를 포함한다.
2. 일반 HTML에서 현재 파서와 Trafilatura를 비교한다. 특허·논문 근거가 빠지지 않는지 확인한다.
3. 반복 요청 처리의 유지보수 부담이 실제로 있을 때 Tenacity를 시험한다.
4. 스캔 문서 지원이 필요하면 Docling을 선택 기능으로 시험한다.

비교할 항목은 불필요 숫자 혼입, 본문 누락, 읽기 순서, 수식·부호 보존, 페이지·단락 위치, 추출 시간, Windows 설치 크기·실패율이다. 속도나 토큰 절감 수치를 추정으로 확정하지 않는다.

추출기가 바뀌면 문장 경계와 문장 ID도 바뀔 수 있다. 기존 보고서의 근거를 새로 추출한 텍스트에 조용히 연결하지 말고, 당시 원문과 추출 버전을 보존해야 한다. PRISM의 구성대비 판단·검증·보고서 조립은 유지하면서 추출 계층부터 작은 범위로 도입하는 것을 권한다.
